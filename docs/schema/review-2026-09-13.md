# Baseline Schema Integrity Review — 2026-09-13

**Status:** Complete for baseline design freeze

This review reconciles `aggregate-design.md` into the canonical `invariants.md` and `schema.sql` baseline.

## Outcome

The aggregate model is internally coherent enough to begin implementation. No additional top-level domain aggregate is required before coding.

The baseline SQL contains 53 tables with explicit tenant ownership, immutable-revision relationships, durable runtime history, async reliability state, notification state, and audit/accounting data.

## Conflicts found and resolved

### 1. Public vs internal Binding

Earlier Binding wording assumed every Binding was publicly exposed. Jobs and Sync later demonstrated the need to reuse the same Operation/Connection/Credential composition without a public route.

**Resolution:** Binding has independent axes:

- `kind = QUERY | ACTION`
- `exposure_mode = PUBLIC | INTERNAL`

Only PUBLIC Bindings may have `BindingPublicIdentifier` rows.

### 2. Job target model

Early Job design assumed every Job invoked a Binding. Later scheduled Sync required a second scheduler target.

**Resolution:** `JobRevision` targets exactly one of:

- stable Binding, or
- stable SyncDefinition.

`JobRun` pins the corresponding immutable BindingRevision or SyncRevision at occurrence materialization.

### 3. Framer-specific Sync core

Early Sync notes placed Framer collection/item concepts too close to generic synchronization state.

**Resolution:** Core Sync tables are provider-neutral. Framer CMS behavior lives in adapter config/capabilities. `SyncMapping` uses generic source/target identities.

### 4. Target uniqueness in generic Sync

A universal unique `(sync_definition, target_identity)` rule would incorrectly assume every target adapter provides exclusive target identity semantics.

**Resolution:** SQL uses nullable `target_exclusive_key`. Adapters populate it only when exclusive mapping is guaranteed; the partial unique index then enforces exclusivity.

### 5. Historical revision pinning

Mutable parent pointers such as `active_revision_id` could be mistaken for historical truth.

**Resolution:** Runtime/history rows always persist exact immutable version/revision IDs. Parent active/current pointers are authoring/admission conveniences only.

### 6. Nullable usage scope

A composite primary key containing nullable `project_id` would accidentally prohibit Workspace-level UsageBucket rows.

**Resolution:** UsageBucket now has UUID identity plus separate partial unique indexes for Workspace scope and Project scope.

### 7. Support/impersonation audit attribution

Audit design referenced support sessions but the initial DDL shape did not include a first-class support-session record.

**Resolution:** Added `support_sessions` and linked AuditEvent to it.

### 8. Billing primary subscription

The design states one primary active recurring subscription per Workspace, but an unconstrained subscriptions table would permit multiple primary active records.

**Resolution:** Added `is_primary` and a partial unique index across active-like subscription states.

## DB-enforced boundaries

The baseline DDL directly enforces, among others:

- Workspace-aware foreign keys for critical tenant relationships.
- one active Membership period per Workspace/User.
- one active Framer link per Project and one active Backend project per external Framer project.
- immutable revision parent ownership and per-parent monotonic-number uniqueness.
- BindingRevision composition belonging to one Connection/Workspace graph.
- stable Action idempotency uniqueness by Binding/key hash.
- one JobRun per `(job_definition_id, scheduled_for)`.
- JobRevision target XOR.
- one active SyncRun per SyncDefinition in V1.
- provider webhook event uniqueness when a provider event ID exists.
- one original Execution per WebhookDelivery and JobRun.
- notification logical dedupe.
- append/history identity and tenant scoping.

## Intentionally domain-service-enforced rules

Some invariants are deliberately not represented as fragile triggers or over-generalized SQL constraints:

- every ACTIVE Workspace retaining an OWNER;
- immutability of persisted revision rows;
- PUBLIC Binding requirement for public identifier creation;
- QUERY Binding cannot publish WRITE OperationVersion;
- Project-to-Connection access at Binding publication/runtime;
- JSON contract/schema validation and compile checks;
- lifecycle admission against Workspace/Project/Connection/Credential/Entitlements;
- scheduler misfire/DST/overlap semantics;
- webhook signature verification and ACK boundary;
- Sync adapter capability checks, schema drift, mark-and-sweep, destructive guard;
- notification required-preference and provider-state rules;
- audit redaction.

These rules must be covered by domain tests and E2E tests.

## Partitioning decision

High-volume tables are designed to become time-partitioned, but the baseline intentionally starts unpartitioned:

- executions / execution_attempts
- usage_events
- job_runs
- webhook_deliveries
- sync_runs / sync_run_items
- audit_events

Partitioning is introduced only after measured volume/query/retention evidence justifies the operational complexity.

## Deferred without blocking implementation

The following remain intentionally open and do not block schema implementation:

- exact commercial prices/allowances;
- infrastructure/cloud provider;
- final identity/auth provider;
- exact data-retention durations;
- Project-level ACL beyond Workspace membership;
- future generic Environment aggregate;
- precise runtime cache-invalidation transport;
- provider-specific Sync adapter capability matrices;
- optional cryptographic audit archival/tamper evidence.
