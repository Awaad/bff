# Schema Integrity Review — Baseline V2

**Date:** 2026-09-13  
**Status:** Accepted hardening pass

## Why V2 exists

Baseline V1 had sound domain architecture but several enforcement/documentation gaps discovered by adversarial DDL testing.

V2 fixes those before implementation.

## Corrected defects

### Optional composite lineage

V1 relied on PostgreSQL `MATCH SIMPLE` FKs with nullable lineage columns. A partially-NULL composite could bypass validation.

V2 uses explicit pair-completeness CHECKs for optional lineage and makes core Execution composition fields non-null.

`MATCH FULL` is deliberately not used on tenant-aware optional FKs containing non-null `workspace_id`/`project_id`, because it would reject the valid all-null optional pair. Explicit CHECK + composite FK provides the intended semantics.

### Execution exact lineage

V1 validated BindingRevision, OperationVersion, ConnectionRevision, and CredentialRevision independently.

V2 adds an explicit lineage mode and a composite FK proving a Binding-backed Execution's entire configuration tuple is exactly the composition pinned by its BindingRevision.

Direct/manual executions have no Binding but still prove Operation and Credential share the same Connection.

### Invariant classification

V1 overused the `DB` label for UUIDv7 generation, immutability, and PUBLIC-Binding semantics.

V2 uses DB / DB-ACL / TX / APP classifications truthfully.

### Database privilege enforcement

V2 adds `security/database-roles.sql`.

Published revisions, UsageEvent, and AuditEvent are write-once under application roles.

ExecutionAttempt uses column-level UPDATE privileges rather than full UPDATE revocation because Attempt lifecycle/result fields legitimately change.

### Persistent drafts

V2 adds dedicated mutable draft tables for Connection, Operation, Binding, Job, and WebhookEndpoint. SyncDraft already existed.

This supports Plugin/Dashboard autosave and test/preview without mutating published history.

### Framer project ownership proof

V2 introduces PENDING_VERIFICATION state and requires verification metadata before a FramerProjectLink can become ACTIVE.

The global external-project uniqueness reservation therefore occurs only after an authenticated proof step has succeeded.

### Retention paths

V2 indexes:

- `idempotency_records(expires_at)`
- `consumer_deduplication(processed_at)`
- active `notifications(expires_at)`
- published `outbox_events(published_at)`

### Webhook payload purge

`webhook_deliveries.payload_ref` is nullable in V2 and paired with `payload_purged_at`.

Metadata/dedupe history can therefore outlive the raw payload without magic tombstone strings.

### Public execution reference

Public runtime errors use `public_execution_ref`, not the UUIDv7 primary key.

UUIDv7 remains an internal time-ordered identifier.

## Still intentionally service-enforced

- Workspace owner preservation
- QUERY→WRITE publication rejection
- Project→Connection access policy
- JSON contract/compiler validation
- runtime lifecycle/entitlement admission
- scheduler DST/misfire/overlap semantics
- webhook cryptographic verification/ACK behavior
- Sync capability/schema/delete-guard semantics
- Notification preference/provider monotonicity
- audit redaction

These require domain and E2E tests.
